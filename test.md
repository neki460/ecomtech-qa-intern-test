### 1.4 Бонус вопрос: Опишите один особо рискованный сценарий
Например, пояс Europe/Berlin, 25.10.2026, в 03:00 часы переводят на 02:00. Будильник сработал в 02:57 ещё по летнему времени, пользователь отложил его на 5 минут. По идее повтор должен быть через 5 реальных минут, то есть в 02:02 уже по зимнему.

Заметить такое сложно. Часы переводят раз в год, ночью, и ещё должно совпасть, что человек именно тогда отложил будильник. Плюс в требованиях не сказано, как считать N минут.В требованиях я скорее всего бы прописал, что N минут отсчитываются по реальному времени, а не по часам на телефоне.

## Задание 2. «Создание заказа» — проверка API и обработки ошибок
### 2.1 Анализ требований
1. Какой код вернётся, если ошибок несколько сразу?
   Т5-Т8 описывают ошибки по одной. Например, товара 101 нет (404), а товара 102 не хватает (409), или quantity = 0 (400), а сервис остатков упал (503). Непонятно, что тогда ждать.
2. Проверяется ли user_id?
   В Т6 только про товар. Не очень понятно, что будет, если user_id не существует или это строчка, и можно ли сделать заказ за другого пользователя.
3. Что если один product_id в запросе два раза?
   Например, на складе 3 штуки, а в запросе две позиции {101, 2}. По отдельности хватает, вместе уже нет. Тут непонятно, ждать 201, 409 или 400.
4. Что считается «положительным целым числом»?
   В JSON нет отдельного типа для целых, так что непонятно, примут ли 2.0 и "2". И есть ли максимум для quantity и количества позиций.
5. Если одного товара нет, отклоняется весь заказ?
   Т4 прямо не запрещает создать заказ частично, а для заказов это иногда важно.
6. Резервируется ли товар при создании заказа?
   Не сказано, меняются ли остатки после заказа. От этого зависят проверки после 201 и что будет, если двое одновременно берут последние штуки.
7. Что если товар есть, но снят с продажи?
   Т6 только про товар, которого нет вообще. Не очень понятно, чего ждать.
8. Что приходит в ответе?
    В Т4 есть только id и статус. Без контракта ответ нормально не проверить.

### 2.2 Чек-лист тестирования
Для quantity (Т3) взял классы (положительное целое подходит, а 0, отрицательное, дробное и null нет) и границы 0 и 1. Для остатка граница это количество, равное остатку (ещё 201), и на 1 больше (уже 409).

| Правило | Данные корректны (Т1-Т3) | Товар есть (Т6) | Сервис остатков работает (Т8) | Остатка хватает (Т7) | Результат |
|---|---|---|---|---|---|
| 1 | нет | - | - | - | 400 |
| 2 | да | нет | - | - | 404 |
| 3 | да | да | нет | - | 503 |
| 4 | да | да | да | нет | 409 |
| 5 | да | да | да | да | 201, status = created |

Перед проверками: пользователь с id 15 есть, товара 101 на складе 5 штук, товара 102 на складе 10 штук, товара с id 999999 нет.

Позитивные:
1. Заказ на 2 штуки товара 101 от пользователя 15. Должен вернуться 201, id заказа и статус created. (Т1-Т4)
2. Заказ из двух товаров, 101 и 102. Заказ создаётся, в нём обе позиции. (Т1, Т2, Т4)
3. Заказ на 1 штуку, это минимальное количество. Заказ создаётся. (Т3)
4. Заказ на 5 штук товара 101, то есть ровно весь остаток. Заказ создаётся. (Т4, Т7)

Негативные:
5. Заказ на 6 штук товара 101, на одну больше остатка. Должен вернуться 409. (Т7)
6. quantity = 0. Должен вернуться 400. (Т3, Т5)
7. quantity отрицательное, дробное или null, каждое отдельным запросом. На каждый 400. (Т3, Т5)
8. Пустой список товаров. 400. (Т1, Т5)
9. Запрос без user_id. 400. (Т1, Т5)
10. Товар без product_id или без quantity, отдельными запросами. 400. (Т2, Т5)
11. Товар, которого нет (id 999999). 404. (Т6)
12. Сервис остатков не отвечает. 503, заказ не создаётся. (Т8)

### 2.3 Тест-кейсы API
#### TC-01. Успешное создание заказа (Т1-Т4)
Предусловия: пользователь 15 есть, товар 101 есть (5 штук), сервис остатков работает, записал, сколько у пользователя заказов (N0).

```http
POST /orders
Content-Type: application/json

{
  "user_id": 15,
  "items": [
    { "product_id": 101, "quantity": 2 }
  ]
}
```

Должен прийти 201 Created. В ответе id заказа и status = created, в базе стало N0 + 1 заказов, у нового нужный user_id, товар и количество. Если есть резерв, остаток 101 стал 3.

#### TC-02. Некорректные данные, quantity = 0 (Т3, Т5)
Взял 0, тк это ближайшее неправильное значение к границе, на нём ловится quantity >= 0 вместо quantity > 0.
Предусловия как в TC-01, чтобы не получить 404 или 503.

```http
POST /orders
Content-Type: application/json

{
  "user_id": 15,
  "items": [
    { "product_id": 101, "quantity": 0 }
  ]
}
```

Должен прийти 400 Bad Request с ошибкой про quantity. Заказ не создан, остаток не изменился.

#### TC-03. Сервис остатков недоступен (Т8)
Предусловия как в TC-01, только сервис остатков остановлен или вместо него заглушка (WireMock), которая отвечает 5xx или молчит дольше таймаута.

```http
POST /orders
Content-Type: application/json

{
  "user_id": 15,
  "items": [
    { "product_id": 101, "quantity": 2 }
  ]
}
```

Должен прийти 503 Service Unavailable. Заказ не создан, остаток не изменился, запрос не висит дольше таймаута. Когда сервис поднимут, тот же запрос должен дать 201 и ровно один заказ.

### 2.4 Проверка результата
201 значит только то, что сервер ответил успешно. Заказ при этом мог сохраниться с другим user_id, без одной позиции или остаток мог списаться два раза.
Что ещё проверю:
1. В ответе есть id и status = created, поля как в контракте.
2. Заказ находится по id, в нём тот же пользователь и ровно те позиции и количества, что я отправлял.
3. Остаток уменьшился ровно на quantity и один раз (если резерв вообще есть).
4. При ошибках заказ не создаётся и остатки не меняются.

### 2.5 Бонус вопрос
Клиент не знает, дошёл ли запрос, выполнился ли он или просто потерялся ответ. Если отправить тот же POST ещё раз, сервер примет его за новый запрос и создаст второй заказ (POST не идемпотентный).

Что в теории может случиться:
- два заказа вместо одного, двойная оплата и доставка;
- товар резервируется два раза;
- повтор получает 409, тк первый заказ уже забрал остаток, и клиент думает, что заказа нет;
- повтор приходит, пока первый ещё обрабатывается, и дубль не ловится.
Вопросы команде:
- есть ли Idempotency-Key или какая-то другая защита от повторов?
- что вернётся на повтор с тем же ключом и что будет, если тело другое?
- может ли клиент перед повтором проверить, создался ли заказ?
- создание заказа и резерв идут в одной транзакции?
Что стоит проверить:
- два запроса с одним ключом дают один заказ и один id;
- тот же ключ с другим телом даёт ошибку;
- два одновременных запроса с одним ключом дают один заказ;
- разные ключи с одинаковым телом дают два заказа.

### 3.2 Вывести общую сумму оплаченных заказов по каждому пользователю (включая пользователей без заказов).
```sql
SELECT u.id,
       u.name,
       COALESCE(SUM(o.total), 0) AS paid_total
FROM users u
LEFT JOIN orders o
       ON o.user_id = u.id
      AND o.status = 'completed'
GROUP BY u.id, u.name
ORDER BY u.id;
```

| id  | name   | paid_total |
| --- | ------ | ---------- |
| 1   | Анна   | 3000       |
| 2   | Борис  | 2500       |
| 3   | Виктор | 1500       |
| 4   | Глеб   | 0          |
LEFT JOIN оставляет Глеба, у которого нет заказов, а COALESCE даёт 0 вместо NULL. Условие на статус стоит в ON, тк в WHERE Глеб бы пропал.

### 3.3 Вывести пользователей, у которых есть хотя бы один заказ со статусом `returned`.
```sql
SELECT u.id, u.name
FROM users u
JOIN orders o ON o.user_id = u.id
GROUP BY u.id, u.name
HAVING SUM(CASE WHEN o.status = 'returned' THEN 1 ELSE 0 END) > 0;
```

| id  | name   |
| --- | ------ |
| 3   | Виктор |

### 3.4 Вывести топ-3 пользователей по сумме оплаченных заказов.
```sql
SELECT u.id,
       u.name,
       SUM(o.total) AS paid_total
FROM users u
JOIN orders o ON o.user_id = u.id
WHERE o.status = 'completed'
GROUP BY u.id, u.name
ORDER BY paid_total DESC
LIMIT 3;
```

| id  | name   | paid_total |
| --- | ------ | ---------- |
| 1   | Анна   | 3000       |
| 2   | Борис  | 2500       |
| 3   | Виктор | 1500       |

Тут обычный JOIN, чтобы в топ не попал Глеб с нулём. Если на третьем месте одинаковые суммы, LIMIT отрежет кого-то наугад, тогда лучше FETCH FIRST 3 ROWS WITH TIES.

### 3.5 Вывести пользователей, не делавших ни одного заказа.
```sql
SELECT u.id, u.name
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
WHERE o.id IS NULL;
```

| id  | name |
| --- | ---- |
| 4   | Глеб |
Остаются только строки, где заказ не нашёлся. NOT IN не использую, тк он ломается, если в user_id есть NULL.

### 3.6 (дополнительно, на оценку) Написать запрос, который выводит для каждого города среднюю сумму одного заказа по оплаченным заказам.

```sql
SELECT u.city,
       ROUND(AVG(o.total), 2) AS avg_paid_order

LEFT JOIN orders o
       ON o.user_id = u.id

ORDER BY u.city;
```
